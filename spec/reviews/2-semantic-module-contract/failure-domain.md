# Failure-domain analysis of the issue #2 semantic-module-contract specification

## Summary

Failure-domain review of the `2-semantic-module-contract` branch: unstated
failure modes, entity-identity confusion, evaluation-purity gaps and
topological edge cases, read against the four checklist axes and against the
one property this module exists to hold — that **"unknown" and "not assessed"
stay distinct from "safe" and from "not applicable", and that schema validity
is never a safety claim**. The base review (`base.md`) covered structure,
coverage bookkeeping and requirement quality; nothing it found is restated
here.

The declared vocabulary holds. `EpistemicState` shares no member with any
ordinal scale, no schema declares a `default`, `negligible`/`E0`/`C0`/`none`
are documented as scored values rather than absences, and the widened lint
allow-lists remove the 0.2.0 nudge towards a scale's safe end. Within the
declaration record, on the axes it names, the property is sound.

The failures are around that record rather than inside it. Six of them are
paths by which an unassessed or unaddressed hazard reads as a handled one:

- The `mitigates` edge that the `unmitigated-hazard` check consumes **cannot
  be authored by any object type declared in the catalog** — the iso
  vocabulary scopes `mitigates` to "Control mitigates a threat/risk/
  vulnerability", the only `allowed_links` carrying it lists `threat`, `risk`
  and `vulnerability`, and no artifact type names `hazard` at all (FND-001).
- Nothing in the bundle asserts that either traceability check ever **fires**;
  every criterion over `traceability` compares it as data (FND-002).
- The forbidden-key seal is `unevaluatedProperties`, a 2020-12-only keyword
  that older and partial validators ignore, so the seal **fails open** where
  `required` fails closed — and what it seals is the hazard/failure-mode
  distinction (FND-003).
- An **absent** `assessment` is a fourth epistemic state the module never
  names, distinct from all three it does (FND-004).
- The declaration record — and therefore every FR-004 guarantee — is reached
  only through a `required: false` locator, so the safety property is **opt-in
  per document** and the document-level gate that always runs is much weaker
  (FND-005).
- Acceptance is bound to neither an assessment nor the content accepted, and
  `accepted` is the only one of six lifecycle states that obliges anything
  (FND-006, FND-009).

Nine mediums and four lows follow: cardinality disagreements that the pending
extraction mapping will have to resolve blind, a vacuous acyclicity guard
beside an unguarded cyclic edge, lint rules that leak across the module
boundary the module exists to draw, and an `imports: {}` whose meaning lives
only in a YAML comment — the module's own epistemic collapse, applied to its
own metadata.

## Verdict

**CONDITIONAL** — FND-001 through FND-006 should be dispositioned before
planning; each is a distinct path by which an unassessed or unaddressed hazard
reads as a handled one, which is the failure this module was created to make
impossible. No spec artifact, schema, manifest or skeleton was edited by this
review.

## Checklist Coverage

| Axis | Result |
|---|---|
| 1. Extension points / trust boundaries | ❌ Three unstated failure policies: OCL clause evaluation (FND-010), `EvidenceRef` target resolution (FND-019), and a dropped object type's effect on validation (FND-017). None chooses strict, resilient or configurable. |
| 2. Entity identity | ❌ Neither object type declares a uniqueness key; record identity (`fields[].identity`) and document identity (frontmatter `id`) coexist unbound, and identity fields are bounded below but not above (FND-011). Skeleton pairs share ids (FND-021). |
| 3. Evaluation purity | 🚧 The schemas are pure — no `default`, no computed value, no inference, and FR-004-CON-2 states it. The gap is the other direction: user-supplied OCL is carried and never evaluated, with an enforced and an unenforced invariant shipped side by side (FND-010). |
| 4. Topological robustness | ❌ The one acyclicity guard covers an edge that cannot cycle; `references`, declared both ways on both types, can and is unguarded, with no termination statement for the FR-058 upward trace (FND-012). Causation can be authored as `references` and escape both (FND-013). |
| Safety property (`not_assessed` ≠ safe) | 🚧 Holds inside the declaration record, on the axes it names. Breaks around it: an absent `assessment` (FND-004), a document that never produces a record (FND-005), a seal that fails open (FND-003) and terminal states reachable over unassessed axes (FND-006, FND-009). |
| Acceptance is authored, never inferred | 🚧 `accepted` requires `provenance`, which is the right rule. It is unbound to the assessment it accepts and to the content version (FND-006), and the three other terminal states require nothing (FND-009). |
| Hazard / failure-mode conflation | 🚧 Type-distinct required and forbidden keys, separate skeletons, separate lint sections. Conflation is reachable only through a validator that ignores `unevaluatedProperties` (FND-003) and through the unscoped lint rules (FND-015). |

## Notes

- The `EpistemicState` design is the strongest part of the bundle and nothing
  here disputes it: three states with disjoint members from every scale, no
  `default` anywhere, `negligible`/`E0`/`C0`/`none` each documented as a scored
  value, and the 0.3.0 lint widening that removes the nudge towards a scale's
  safe end. FND-004 is not an argument against it — it is the observation that
  the same discipline stops at the edge of the record, and that the states the
  module names are outnumbered by the ways a value can be missing.
- FND-001 is the only finding this repository cannot fix alone. It is recorded
  as a specification gap rather than a defect of this branch: the branch
  inherited the `traceability` model unchanged from 0.2.0 by deliberate
  decision (NFR-001-AC-4), so the unauthorable edge predates it. It still
  belongs in the record, because `spec.md` scopes out fourteen dependencies by
  name and this one is not among them, and because promotion (`quoin#290`)
  would ship a check that cannot fire.
- FND-008 and FND-014 are cheap now and expensive later: the first fixes a
  shape before an extractor is written against it, the second is a manifest key
  and a requirement sentence.
- No spec artifact, schema, manifest, skeleton or test was edited by this
  review. Findings are reported for disposition by the branch author.
